# Стратегія тестування

**Проєкт:** QA сервісу платежів для мерчантів\
**Стек тестування:** Playwright, TypeScript, Ajv та JSON Schema\
**Середовище:** Docker, PostgreSQL та Stripe test mode

## 1. Що тестувалося і навіщо

Тестування охоплювало створення, отримання та перегляд списку платежів, capture, повернення коштів (refund), вебхуки, валідацію вхідних даних, контракти відповідей API та основний UI-сценарій checkout.

Найбільше уваги приділено backend API, оскільки він містить ключову платіжну логіку і безпосередньо впливає на фінансовий стан. Покриття включає успішні платіжні сценарії, відхилені платежі, некоректні вхідні дані, граничні випадки, ручний capture, повні та часткові refund, а також поведінку ідемпотентності.

Сценарії capture і refund містять випадки, коли Stripe відхиляє операцію. Ці перевірки важливі, оскільки локальний сервіс не повинен повідомляти про успішну фінансову операцію, якщо провайдер її відхилив. За потреби перевірявся стан бази даних, щоб підтвердити коректну поведінку платежів, refund та вебхуків.

Перевірки вебхуків зосереджені на валідації підпису та обробці дублікатів подій. Оскільки події можуть асинхронно змінювати стан платежу, підроблені або повторно оброблені події можуть призвести до некоректних статусів чи дублювання бізнес-ефектів.

Схеми відповідей API та основний сценарій checkout також протестовано, щоб покрити стабільність контрактів та інтеграцію frontend і backend. Детальні перевірки бізнес-правил зосереджені на рівні API, де збої легше локалізувати.

## 2. Типи тестів

- **Ручне дослідницьке тестування:** використовувалося для вивчення поведінки платежів, аналізу відповідей API та стану бази даних, а також для документування відтворюваних дефектів з обґрунтованою критичністю (severity).
- **API-інтеграційні тести:** написані з використанням Playwright і TypeScript для перевірки HTTP-ендпоінтів та інтеграції сервісу зі Stripe і PostgreSQL. Цей рівень забезпечує основне покриття платіжних сценаріїв, валідації, обробки помилок та консистентності стану.
- **Контрактні тести:** використовують Ajv і JSON Schema, що зберігаються поряд із тестами, для перевірки структури відповідей, обов'язкових полів і типів даних. Вони допомагають виявляти неочікувані зміни у відповідях API.
- **E2E-тести:** використовують Playwright та Page Object Model для перевірки основного сценарію checkout через браузер і підтвердження того, що frontend і backend працюють разом.

Автоматизовані тести запускаються локально та через GitHub Actions. CI піднімає Docker-середовище, очікує на health-ендпоінт і запускає набір тестів Playwright. Тести відомих дефектів використовують `test.fail(...)` для фіксації очікуваних падінь. Тому успішний запуск CI не означає, що всі зареєстровані дефекти виправлено; ці тести слід переглядати при зміні поведінки застосунку.

## 3. Покриті ризики

- **Дублювання обробки платежів:** повторні запити на створення та дубльовані події вебхуків перевіряються на ідемпотентність, щоб виявити дублікати записів або бізнес-ефектів.
- **Некоректні фінансові суми:** валідація capture, overcapture, null-суми capture та поведінка часткових refund перевіряються для виявлення недійсних або неконсистентних сум.
- **Хибний фінансовий успіх:** сценарії невдалих capture і refund перевіряють, чи не фіксує локальний сервіс помилково успіх після відхилення операції з боку Stripe.
- **Некоректний стан платежу:** перевірки життєвого циклу платежу аналізують статуси та збережений стан під час створення, capture, refund і збоїв.
- **Безпека та цілісність даних:** перевірки підпису вебхуків покривають підроблені події; витік client secret покритий окремим тестом дефекту. Це точкові перевірки безпеки, а не комплексний аудит безпеки.
- **Некоректні вхідні дані та нестабільність API:** граничні випадки валідації та пагінації перевіряють обробку помилок, а валідація за JSON Schema перевіряє структуру відповідей і типи даних.
- **Збої UI-інтеграції:** E2E-тести checkout перевіряють основний клієнтський сценарій на рівні frontend і backend.

Ці ризики покриті тестами, але залишаються невирішеними там, де тести відтворюють відкритий дефект.

## 4. Поза межами тестування

- **Unit-тестування:** застосунок надається як Docker «чорна скринька» без доступу до вихідного коду, тому внутрішні функції та модулі безпосередньо не тестуються.
- **Внутрішня логіка Stripe:** Stripe розглядається як зовнішній провайдер. Тестування зосереджене на інтеграційній поведінці Merchant Payment Service та обробці відповідей і подій провайдера.
- **Тестування продуктивності та навантаження:** перевірка ємності, пропускної здатності та масштабованості виходить за межі функціонального тестування цього проєкту.
- **Широке покриття браузерів та UI:** UI-автоматизація зосереджена на основному сценарії checkout; повна матриця крос-браузерного тестування та вичерпні UI-перевірки не включені.
- **Продакшн-платежі:** усі платіжні сценарії використовують Stripe test mode і тестові дані. Реальні картки та реальні кошти поза межами тестування.
- **Комплексна оцінка безпеки та відповідності вимогам:** тестування на проникнення (penetration testing) та формальна перевірка відповідності PCI DSS не включені.
- **Інфраструктура та адміністрування баз даних:** стійкість розгортання, резервне копіювання та адміністрування БД виключені. Перевірка бази даних використовується лише для підтримки функціональної верифікації.
